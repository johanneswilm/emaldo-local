Apply policy sends the mode and limits to the battery; each change is checked and rate-limited, and with writes off it only records what would happen. Undo my last change puts back the inverter limits that were in place before this software first changed them.

In bridge mode the module owns the hardware: the engine writes the 96-slot override table the vendor app and Home Assistant already use, so the limits below are recorded in this installation's config and the plan is what reaches the module.

Day schedule (96 quarter-hour slots)

Written to the module as the vendor set_override command (0x1a) — the same command Home Assistant's optimizer uses. Slot 0 is 00:00 local; slot n is n·15 minutes after midnight. A second set of 96 covers the following day, which is what the vendor app does.

Work mode and limits (vendor commands)

Sent as the module's own settings commands, the ones the vendor app writes.

    Role

    Bridge: the vendor app stays the hardware controller and this service fronts its cloud. Driver: this service replaces the vendor app on the Modbus/CAN/MCU buses and the vendor supervisor is parked. Either direction is one unit command (systemctl enable --now emaldo-local[-driver]) and the page comes back on the same address and port.

    Operating mode

    Local: the vendor domains resolve to this box and the vendor app runs against the built-in bridge. Vendor: the pins are removed and the bridge's cloud leg passes traffic through, so the app resumes its original cloud path. Either switch is one command and reversible; the app is never disabled.

    Cellular (LTE)

    The vendor app dials the built-in LTE modem as a fallback path. While the unit runs local that path is closed (modem unbound from USB, pppd stopped, interface down) because it is the only way to reach the vendor cloud. Restoring puts the modem back on the bus; the app redials by itself.
